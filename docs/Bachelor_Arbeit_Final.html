1. Einleitung und Aufgabenstellung

1.1 Projektziel

Ziel dieses Projektes war die Entwicklung einer robusten Softwarelösung für einen KUKA-Industrieroboter (Steuerung KRC4), der in der Lage ist, das Spiel "Connect Three" (eine vereinfachte Variante von "4 Gewinnt" auf einem 6x4-Raster) autonom gegen einen Menschen oder gegen sich selbst zu spielen. Das Projekt demonstriert die Interaktion zwischen komplexer High-Level-Logik (KI, Spielregeln) und Low-Level-Hardwaresteuerung (Kinematik, E/A-Signale).

1.2 Anforderungen (Lastenheft)

Gemäß dem Lastenheft ("2023-03-06-IRL-HeB-E-O-1") mussten folgende funktionale Anforderungen erfüllt werden:

  • Spielfeld: Ein horizontales 6x4-Raster mit physikalischen Magazinen für Rote und Blaue Steine.
  • Spielmodi: Drei Betriebsarten müssen unterstützt werden:
    1. Mensch gegen Mensch (Roboter als reiner "Dealer")
    2. Mensch gegen Roboter (Interaktives Spiel)
    3. Roboter gegen Roboter (Autonome Demonstration)
  • Softwarequalität: Der Code muss modular, dokumentiert und robust gegen Fehlbedienung sein.

2. Systemanalyse und Entwurf: Evolution der Architektur

2.1 Von der Einzeldatei zur modularen Lösung

In der frühen Entwicklungsphase wurde das Programm zunächst monolithisch strukturiert, um schnelle Funktionstests zu ermöglichen (GAME_LOGIC (1).src). Mit steigender Komplexität – insbesondere durch die Einführung der drei Spielmodi und der KI – zeigte sich jedoch, dass eine Modularisierung signifikante Vorteile für die Stabilität und Wartbarkeit bietet.

Vorteile der neuen Architektur:

  1. Kapselung (Separation of Concerns):
    Die Trennung von Logik (GAME_CTRL) und Bewegung (ROBOT_MOTION) erlaubt es, die Spielregeln zu testen, ohne den Roboter physisch zu bewegen (z.B. in der Simulation). Umgekehrt können Bewegungen optimiert werden, ohne die Spiellogik zu gefährden.
  2. Vermeidung von Linker-Konflikten:
    KRL (Kuka Robot Language) unterscheidet strikt zwischen lokalen und globalen Daten. Durch die Auslagerung aller gemeinsam genutzten Variablen in eine zentrale GAME_DATA.dat mit dem Schlüsselwort PUBLIC werden Zugriffskonflikte und "Declaration not found"-Fehler effektiv vermieden. 
    DEFDAT GAME_DATA PUBLIC
   GLOBAL CONST INT MODE_RVR = 2 ; Zentral definierte Konstante
   DECL GLOBAL INT Board[4,6]    ; Globales Spielfeld
ENDDAT
  3. Wiederverwendbarkeit:
    Das Modul ROBOT_MOTION stellt generische Funktionen wie PERFORM_GAME_MOVE bereit, die von allen drei Spielmodi gleichermaßen genutzt werden.

2.2 Entwurf der Schichten-Architektur (Layer Model)

Modul Rolle Verantwortung
MAIN.src Controller State Machine. Verwaltet den Programmfluss, Initialisierung (Smart Start) und den Replay-Loop.
GAME_CTRL.src Model / Logic Regelwerk & KI. Enthält das virtuelle Spielbrett (Board[,]). Berechnet Züge, prüft Gewinner.
ROBOT_MOTION.src View / Hardware Aktorik. Setzt logische Befehle ("Setze Stein auf 2,3") in physische Bahnplanung um.
GAME_DATA.dat Database Globale Daten. Zentraler Speicher für Konstanten (ROWS, COLS), Positionen und Zustände.

3.4 Technischer Exkurs: Das "Status & Turn" Problem und die Lösung

Eines der größten technischen Hindernisse war die Berechnung von Zielpunkten zur Laufzeit.

Das Problem:
Eine KRL-Koordinate vom Typ E6POS enthält neben kartesischen Koordinaten (X, Y, Z) auch Achskonfigurationsdaten (Status und Turn).

  • Status: Informationen über die Lage des TCP (z.B. Überkopfbereich).
  • Turn: Vorzeichen der Achswinkel (z.B. Achse 4 bei +10° oder -350°).

Berechnet man einen Punkt rein mathematisch (pNeu.X = pAlt.X + 50), bleiben S und T von pAlt erhalten. Wenn pNeu eine andere Achsstellung erfordert, meldet die Steuerung: "Position unerreichbar".

Die Lösung: Der "Frame-Trick"
Wir nutzen einen impliziten Cast auf den Datentyp FRAME (der S/T ignoriert).

DECL E6POS pTarget
DECL FRAME fMove

; 1. Zielpunkt holen (hat noch alte S/T Werte vom Referenzpunkt)
pTarget = P_FIELD[row,col]

; 2. Der Cast auf FRAME entfernt S und T
fMove = pTarget 

; 3. PTP-Bewegung: Steuerung berechnet Achswinkel neu ("Shortest Way")
PTP fMove

4. Funktions- & Variablen-Referenz

4.1 Globale Variablen (GAME_DATA.dat)

  • Board[4,6] (INT): Das 2D-Array, das den Spielzustand speichert. 0=Leer, 1=Rot, 2=Blau.
  • GameMode (INT): Aktiver Modus. 0=HvH, 1=HvR, 2=RvR.
  • UsedRed, UsedBlue (INT): Zähler für verbrauchte Steine im Lager.

4.2 Wichtige Funktionen

GAME_CTRL.src

  • GET_AI_MOVE(myColor): Gibt die optimale Spalte (1-6) für die KI zurück.
  • GET_GRAVITY_ROW(col): Simuliert Physik. Iteriert von unten nach oben.

ROBOT_MOTION.src

  • PERFORM_GAME_MOVE(row, col, player): Der zentrale Bewegungsblock. Holt Stein -> Frame-Trick -> Setzt Stein.
