IF (GameMode == MODE_HVR) AND (CurrentPlayer == FALSE) THEN

Alles korrekt.

B. Optimierungspotenzial (Robotik & Motion)

1. Überschleifen ($APO)

Derzeit nutzen Sie reine Genauhalt-Bewegungen (PTP fMove, LIN fMove). Das führt zu einem "stotternden" Ablauf, da der Roboter an jedem Punkt kurz anhält (v = 0).

Vorschlag: Verwenden Sie Überschleifen für die Anfahrtsbewegungen.

  • PTP: $APO.CPTP = 50 (50% Überschleifen)
  • LIN: $APO.CDIS = 10 (10mm vor Ziel verrunden)

Code-Beispiel (ROBOT_MOTION.src):

; In ROBOT_MOTION_INIT einfuegen:
$APO.CDIS = 20.0 ; mm
$APO.CPTP = 50   ; %

; Anwendung (z.B. PERFORM_GAME_MOVE):
fHelp = pHigh
PTP fHelp C_PTP ; <--- Schwungvolles Anfahren
fHelp = pPick
LIN fHelp ; <--- Letzter Punkt muss genau sein (kein C_DIS)!

Risiko: Im Magazin (XP_MAG) darf NICHT überschliffen werden, wenn der Greifer in die Vorrichtung eintaucht, sonst droht Kollision. Nur "in der Luft" überschleifen!

2. Logik-Trigger statt WAIT SEC

Sie verwenden WAIT SEC 0.5 nach dem Greifen. Das kostet Zykluszeit.
Besser: Nutzen Sie Greifer-Sensoren (falls vorhanden), um direkt weiterzufahren, sobald der Greifer "Zu" meldet. 

; Statt:
; WAIT SEC 0.5

; Besser (wenn Sensoren auf EINGANG 33/34 liegen):
; GRIPPER_CLOSE()
; WAIT FOR $IN[34] ; Warten bis Sensor "Zu" signalisiert

Falls keine Sensoren verbaut sind, ist WAIT SEC unumgänglich, kann aber oft auf 0.2s reduziert werden.

C. Lastdaten (Load Data) - Anti-Gravity Check

Ihr Code setzt $TOOL = TOOL_DATA[14]. Aber das physikalische Gewicht (LOAD_DATA) fehlt. Wenn der Roboter nicht weiß, dass er einen Greifer (und evtl. einen Stein) trägt, stimmt die Bahnplanung nicht perfekt ("Overshoot" oder Zittern).

To-Do für den User:
Setzen Sie die Lastdaten explizit vor der Bewegung.

; Beispiel in ROBOT_MOTION_INIT:
$LOAD.M = 1.5     ; Masse in kg
$LOAD.CM = {X 0, Y 0, Z 50, A 0, B 0, C 0} ; Schwerpunkt
; Oder wenn in Config.dat definiert:
; BAS(#TOOL, 14) ; Setzt TOOL + LOAD, wenn korrekt konfiguriert.

D. Sicherheitshinweise ("Der Frame-Trick")

Sie nutzen den Frame-Trick (fMove = pTarget), um Status/Turn zu löschen.
Vorteil: Roboter findet den Weg selbst, keine "Unerreichbar" Fehler bei berechneten Punkten.
Risiko: Der Roboter könnte eine Achskonfiguration wählen, die Sie nicht erwarten (z.B. Ellenbogen unten statt oben). Da das Spielbrett flach ist, ist das Risiko gering.
Empfehlung: Testen Sie einmalig in T1 bei allen vier Ecken des Feldes, ob der Roboter "umschlägt" (Achsen dreht). Falls ja, müssten Sie für extreme Positionen doch Status/Turn vorgeben.
